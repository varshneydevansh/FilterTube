# Opt-in peer-to-peer Auto-sync — extension candidate

Date: 2026-10-24. This document separates implemented extension behavior from installed, physical-network and downstream app acceptance. Nothing is enabled for existing users, published, pushed or copied into native runtime mirrors by this change.

## Ordinary interaction

Accounts & Sync now has a visible **Peer-to-peer sync** section beside the existing device flow. Existing manual pairing, Copy once, parent Send, backup and optional pickup controls remain available.

The initial screen shows one next step: **Add a device, verify it, then choose what to sync.** Empty parent selectors and disabled personal-link forms stay hidden. One managed route displays its recipient directly; multiple routes use a selector. Personal choices appear only for an eligible verified session. Saved personal links keep additional setup behind **Link another profile**. Read failures remain visible instead of being mistaken for an empty account, and focus returns to a visible heading when a section disappears. **How Auto-sync works** keeps secondary explanations collapsed; the visible footer still states the requirement to keep both Accounts & Sync pages open and connected.

The pairing drawer now follows **Connect → waiting for the other device → match the safety phrase → share or sync**. The existing connection purpose is still chosen before the handshake; presentation does not change roles afterward. Empty QR/link placeholders, disabled future actions, duplicate mode explainers and raw endpoint tables no longer fill the initial view. A real code appears while waiting; the safety phrase takes its place after connection. Existing controller permissions still decide whether Send, Trust and recipient selectors are available. Multi-child recipient checkboxes remain in the visible sharing form, and More options stays reachable throughout the session. Scanner controls retain their own lifecycle. Focus captured before a button is disabled moves to the next visible stage control.

Advanced connection options retain optional pickup setup/check controls with simpler rows. Repeated guides and decorative status chips are hidden; support evidence has its own closed disclosure. Configured pickup status remains visible outside the closed section so an active delivery service is not concealed.

- **Parent updates:** choose the saved connection showing `local child rules → fixed receiving child · device`, then explicitly Turn on Auto-sync. Fresh parent authorization is required. Each new consent has its own generation. Only the link's already approved policy areas are sent.
- **Your other devices:** open and unlock the intended account profile at each endpoint, use the existing code/QR and matching safety phrase, and save the personal device link. Choose Settings and filter rules, Saved video notes, or both. Link this profile requests a separate permission; both endpoints approve that exact profile mapping.
- New personal setup requires both clients to advertise Auto-sync version 1. A legacy saved device alone is not personal synchronization permission.
- Auto-sync defaults off. Turning it off removes the matching local enrollment and queued payloads. It does not delete data already received on another device.
- Use **Needs review → Review settings conflict** for concurrent settings changes. Keep this device or Use other device requires explicit confirmation. Notes keep causal edit/delete conflicts for the existing Notes editor to review.

## What “peer-to-peer” means here

Automatic payload delivery uses the existing confirmed Nanah WebRTC connection between the user's devices. It does not upload personal settings or Notes to a new central profile store, public torrent network, Home Pickup or Internet Pickup service. Existing optional manual pickup paths retain their documented confidentiality and authorization boundaries.

**Both Accounts & Sync pages currently need an active, verified direct connection.** Merely reconnecting a computer to Wi-Fi is not a new Nanah session. This change does not add automatic saved-peer rendezvous, a hidden always-on dashboard, a native daemon, mobile background execution or wake a closed browser. Existing pairing/reconnect establishes the channel; queued authorized changes then resume automatically.

A background alarm wakes existing dashboards roughly once a minute, subject to browser scheduling; it performs no transport and creates no tabs. Dashboard startup, a relevant profile/Notes/trust change, visibility return, network online and managed receiver readiness also trigger checks. Queued state survives dashboard/browser restart. There is no guarantee of instantaneous delivery.

Current WebRTC configuration has STUN and no TURN relay. Separate-network reachability through restrictive NAT/firewall configurations remains an acceptance gate. Without an available peer holding the update, delivery waits. An optional future encrypted store-and-forward path can improve non-overlapping availability, but must be separately consented and labeled.

Official constraints: [Chrome worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle), [WebRTC relay guidance](https://webrtc.org/getting-started/turn-server).

## Authority and data boundaries

| Area | Boundary |
| --- | --- |
| Parent → child | Existing signed managed-policy validation, fixed remote child/device, pinned signing parent/key/version, owning local parent and chosen local rules child. No active-profile target fallback. |
| Receiver consent | Automatic managed dispatch requires saved auto-apply permission and a ready signal for the exact link from the current confirmed receiver session. Existing reconnect approval is respected. No receiver permission is changed by sender enrollment. |
| Personal profiles | Active, unlocked account profile on each device; explicit reciprocal grants pin both profile/device IDs, both grant IDs/generations, selected areas and Ed25519 public keys. Children cannot publish personal settings or create administration grants. |
| Personal settings | Explicit selectors for rule lists/modes, supported content toggles, Main/Kids content filters and categories, languages and legacy aliases. Ownership, PINs, trust, viewing grants and managed time-policy authority remain excluded. No full-account automatic import. |
| Settings conflicts | Field/group three-way merge against the last accepted remote base. Arrays are atomic. Deletions propagate. A locally changed observed base fails before write; conflicting edits require review. |
| Notes | Existing format-1 causal revisions, concurrent heads and deletion tombstones. Exact authorized profile remapping. Sync merges share the editor's background repository queue. Writer credentials and temporary drafts never enter payloads. |
| Revocation | Trust/key/scope/owner/security changes invalidate pending managed consent. Personal grants pin the saved peer identity; unlink/re-pair cannot revive old consent. Profile switching/unlock expiry pauses; it does not substitute another profile. |
| Local storage | `ftDeviceAutoSyncV1` contains private grants/keys; `ftAutoSyncQueueV1` contains bounded pending delivery state. Ordinary import rollback excludes both keys, just as it excludes private Notes/writer state. These keys are not backup payloads or webpage messages. |

**Managed scope coverage is narrower than personal settings sync.** Approved parent updates include Main mode/rule lists, Kids-owned mode/lists and supported Kids filter groups, plus viewing access and normalized time limits when those separate scopes were approved. General child settings toggles (for example, hide Shorts or disable autoplay), top-level/Main content filter groups and child Notes are not represented by current managed grants. Existing grants have not been silently expanded. Personal own-account sync cannot be used to bypass child restrictions.

Personal receiver setup stays unconfirmed until matching signed data/confirmation proves source adoption. Concurrent first invitations select one deterministic handshake. Lost setup acceptance can be retried with the same bounded invitation and exact previously approved mapping; a fresh replacement of an unconfirmed setup still requires explicit receiver consent. No unsolicited acceptance creates trust.

## Delivery state and recovery

The queue is separate from policy authority. It persists consent generations and immutable signed payloads, coalesces newer unsent changes by area, checks authority around asynchronous dispatch, and uses bounded exponential retry. A stale completion or receipt cannot clear a newer edit or consent generation.

Managed revisions are reserved under the existing shared trust-storage lock before a payload is queued. Reserved is neither Sent nor Applied. Separate pages cannot allocate the same revision to different hashes. Existing manual sends observe that reservation floor. No private signing material is added to envelopes.

Personal messages and Applied/Needs review receipts bind the complete profile/device/grant tuple, sequence, message ID and digest with Ed25519 signatures. A known authenticated duplicate can return its prior receipt. Notes retain tombstones; settings snapshots do not use wall-clock last-writer wins.

New managed signatures also bind the full canonical payload using a signed SHA-256 digest. The earlier 32-bit policy hash remains a compatibility field, but no longer decides revision reuse alone: sent, reserved and accepted state preserve the strong digest, and equal-revision digest conflicts fail closed. A real `Aa`/`BB` legacy-hash collision regression covers both tamper rejection and correct revision advancement. Digest-absent legacy signatures remain accepted for compatibility and retain their older, weaker payload-binding boundary; they are never labeled as carrying the new digest. Older native receivers have not been tested with this optional signed field, so this is not a native compatibility claim.

Visible states distinguish **Off**, **Waiting for device**, **Waiting for confirmation**, **Up to date**, **Paused** and **Needs review**. Dispatch/queue acceptance cannot claim application. Existing managed receipts retain their pre-existing trust model; they are not newly cryptographic receiver signatures.

Limits are intentional: at most 64 combined enrollments, 256 queued areas, 512 KiB per payload and 4 MiB queue state. Notes' existing per-note/format bounds still apply. Invalid or oversized data must pause for review instead of sending an obsolete queued snapshot. Retry and failure on one profile must not erase unrelated local settings or notes.

## Implementation ownership

- `js/auto_sync_queue.js`: durable queue and receipt CAS.
- `js/auto_sync_wakeup.js`: browser alarms and wake signals only.
- `js/managed_auto_sync.js`: managed enrollment identity/authority bindings.
- `js/nanah_managed_live_policy.js`: existing signed payloads plus immutable snapshots and revision reservation.
- `js/personal_sync.js`: strict personal grant/payload/signature, settings merge and Notes mapping contracts.
- `js/personal_auto_sync_runtime.js`: reciprocal personal setup, direct delivery, receipts and conflict review.
- `js/device_auto_sync.js`: orchestration, opt-in persistence and managed dispatch.
- `js/device_auto_sync_ui.js`, `css/device-auto-sync.css`: responsive presentation and stable focus.
- `js/nanah_pairing_ui.js`: staged pairing presentation only; it never enables controls, changes trust, selects recipients or sends data.
- `js/nanah_sync_adapter.js`: full-payload SHA-256 binding for new managed signatures, legacy compatibility and accepted-state digest validation.
- `js/tab-view.js`: actual session, approval, settings write and private Notes adapters.
- `js/video_notes_background.js`, `js/video_notes_store.js`: extension-only bulk Notes API using the existing repository queue.

No native worktree, runtime mirror, TV emulator or Android app was modified. This contract is integration input, not extension↔Android/TV interoperability proof. Older clients do not gain personal auto-sync implicitly.
